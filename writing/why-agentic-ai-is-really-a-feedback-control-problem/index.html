Why Agentic AI Is Really a Feedback-Control Problem

Reliable agents need more than tools: observations that change decisions, memory that preserves evidence, and actions that make uncertainty worth resolving.

2026-11-21

An agent’s tools determine what it can do. Its feedback loop determines whether it can respond to what actually happened.

In the previous essay, I followed the connection between reinforcement learning and control theory: a policy is a controller, and an action matters partly because of the future it creates. I want to bring that perspective to a system that looks less like a motor or a budget allocator: a language-model agent trying to fix a bug.

Give it a shell, a code editor, and a test runner. It reads the program, changes a function, runs a test, and receives an error. What happens next?

It might make another plausible edit. It might repeat the test. Or it might notice that the error contradicts its explanation and investigate a different cause. All three behaviors can produce an impressive-looking tool trace. Only the last tells us clearly that evidence changed the decision.

I think reliable agentic behavior depends on closing the loop between action, observation, and revision. When the available observations cannot distinguish the explanations that matter, the agent must also decide what to measure next.

That is why feedback control feels like a useful starting point. It directs attention toward the relationships between components: what the agent can observe, what it believes, how that belief changes its actions, and whether the resulting behavior remains useful when something goes wrong.

Where is the loop closed?

A fixed sequence of actions is open loop with respect to outcomes it never uses. A feedback policy chooses its next action using observations of what happened. The distinction is about dependence on evidence, not whether a language model or a handwritten program makes the decision. A scripted workflow with conditional branches can use feedback. A model with many tools can ignore it.

For an agent, a simple description is:

at∼π(⋅∣mt,g),st+1=F(st,at,wt),ot+1=G(st+1,at,vt+1),mt+1=U(mt,at,ot+1,g).\begin{aligned} a_t &\sim \pi(\cdot\mid m_t,g),\\ s_{t+1} &= F(s_t,a_t,w_t),\\ o_{t+1} &= G(s_{t+1},a_t,v_{t+1}),\\ m_{t+1} &= U(m_t,a_t,o_{t+1},g). \end{aligned}

Here sts_t is the environment state, mtm_t is the agent’s internal memory, and gg is its goal. The disturbances wtw_t and measurement noise vt+1v_{t+1} represent influences the agent does not fully control or observe. Crucially, the memory update includes the action that produced the observation. A test result means little without knowing what was tested.

For the debugging agent, state includes the code version, dependencies, running processes, and inputs. An observation might be a test report from only one part of that state. An action could edit the program or inspect its execution environment. Tools can therefore serve as both actuators and sensors.

The policy and update rule can remain fixed throughout this process. Changing a hypothesis in memory is enough to change behavior, even if no model weights are updated. Feedback within a task, learning across tasks, and improving the learning procedure are separate claims.

I would ask where the feedback enters. Does a failed assertion alter the next edit? Does a timeout change the estimate of whether a process is still running? Does a successful tool call establish that the user’s task is complete, or only that one command executed?

The control perspective helps separate these questions. It does not make a thermostat and a research agent equally capable, or provide a complete definition of agency. Feedback is an architectural property whose usefulness depends on what the loop contains. Åström and Murray, Feedback Systems.

Memory is part of state estimation

Suppose the agent sees the same failing assertion after an edit. It could conclude that the edit did not help. But perhaps the test ran against an old build. Perhaps the dependency environment differs from the one the agent inspected. The same visible failure can arise from different hidden states, and those states call for different actions.

This is the problem of partial observability. In a specified probabilistic model, a belief state represents a distribution over the possible current states, conditional on the action–observation history:

ht=(o0,a0,o1,…,at−1,ot),bt(s)=P(st=s∣ht).h_t=(o_0,a_0,o_1,\ldots,a_{t-1},o_t), \qquad b_t(s)=P(s_t=s\mid h_t).

Under the model’s assumptions, that distribution can summarize the history needed for future decisions. Kaelbling, Littman, and Cassandra develop this idea in their treatment of partially observable decision processes. An agent’s textual memory may approximate such a summary, but it is not automatically a calibrated belief state. Kaelbling, Littman, and Cassandra, 1998.

This changes what I would want memory to preserve. “The patch failed” is a conclusion. “Test X failed on commit Y in environment Z, while the new build was still running” is evidence that permits a different conclusion. Compressing the second into the first can destroy the distinction needed to choose the next action.

An observer in control theory estimates hidden state using both inputs and measurements. Agent memory can serve an analogous function when it keeps observations connected to actions, versions, and unresolved hypotheses. Åström and Murray, Output Feedback.

A useful memory should therefore help answer a practical question: what would I do differently if this part of the record were missing or wrong? Retaining every sentence is unnecessary. Retaining the difference between a completed test and an unconfirmed execution may be essential.

A test result is not yet a judgment

Observation and evaluation are different operations. “The test returned success” describes an event. “The bug is fixed” interprets that event against a goal and a set of assumptions.

The debugger needs to know whether the test exercised the reported failure, whether it ran on the current code, and whether a change broke something else. A green result from an irrelevant test can be perfectly accurate and still fail to answer the question.

This connects to the evaluator essay, but the emphasis here is operational. A misleading judgment does more than produce a bad score. It chooses the next action. An agent that interprets an inconclusive result as failure might make unnecessary edits. One that interprets it as success might stop before verifying the repair.

I would keep at least three things distinct in the record: what was observed, what the agent infers, and what would change that inference. A timeout is an observation. “The process failed” is one possible explanation. Checking process status is an action that can distinguish it from “the process is still running.”

The loop closes usefully when those distinctions affect behavior. Generating a reflection that is never consulted, or converting every error into the same retry, provides much weaker evidence of adaptation.

What existing agent research makes visible

ReAct interleaves language reasoning with actions and observations from an environment. In the paper’s formulation, a reasoning step updates the agent’s context without itself producing external observation feedback. That is a valuable distinction: reasoning can reorganize evidence or suggest a test, while a tool interaction can supply information the model did not already have. The paper also documents failures involving repetitive reasoning and unhelpful search results. Closing a loop does not ensure that each component works well. Yao et al., ReAct, 2023.

Reflexion makes another part explicit. Its agents use task feedback to generate verbal reflections that are retained in memory for later attempts, without updating model weights. That creates a route by which one attempt can influence the next. Shinn et al., Reflexion, 2023.

What interests me is the connection each design creates. ReAct connects reasoning to environmental observations during a trajectory. Reflexion connects feedback to later behavior through retained text. In either case, I would still want to know whether the observation is relevant, whether the reflection is justified, and whether the next decision actually improves because of it. A remembered explanation can preserve a mistake as readily as a lesson.

Planning a little, then checking

Suppose the debugging agent plans to rebuild the package, rerun the failing test, and patch the suspected function. A fresh build might resolve the failure before the patch is needed. Executing the whole sequence without inspecting intermediate outcomes would discard that opportunity to revise the plan.

Model predictive control offers a useful comparison. It predicts ahead, selects actions, executes the first, and solves again using the new state estimate. This is a particular control method with explicit models, objectives, and constraints. A language agent that replans follows a similar pattern, but does not inherit MPC’s guarantees merely by using the same rhythm. Rawlings, Mayne, and Diehl, Model Predictive Control.

The practical question is where to place observation points. Checking after every trivial step may be expensive. Waiting until after several dependent changes may make a failure difficult to diagnose. I would prefer a checkpoint when its outcome could materially change what comes next.

Delay makes this more subtle. A long-running test can return after the agent has made another edit. That result describes an earlier version of the system. If memory records it as evidence about the current version, replanning more often may simply propagate the wrong interpretation faster. Execution identifiers, timestamps, and versioned artifacts help establish which action a measurement actually evaluates.

A short planning horizon is therefore useful only if the observations arriving between plans are informative and correctly attributed.

When a diagnostic is worth more than a fix

Now suppose the agent has two explanations for the failure: HCH_C, a code defect, and HEH_E, an environment mismatch. It can attempt a code repair or an environment repair. Which should it choose?

Let us make a deliberately small hypothetical decision problem. Exactly one explanation is true. Each repair succeeds if and only if it addresses that explanation. There is one final repair attempt, and both repairs have equal cost. Success has utility 1, failure 0. Assume:

P(HC)=0.6,P(HE)=0.4.P(H_C)=0.6,\qquad P(H_E)=0.4.

Without another observation, the best choice is the code repair, with expected utility 0.60.6.

Before committing, the agent can run a diagnostic DD that returns ++ or −-. Suppose its response probabilities are:

Diagnostic outcome Code defect HCH_C Environment mismatch HEH_E
++ 0.9 0.2
−- 0.1 0.8

These are assumed probabilities for the example, not measured accuracies. The diagnostic does not repair the system or change which explanation is true. It provides information before the one repair attempt.

A positive result has probability 0.6(0.9)+0.4(0.2)=0.620.6(0.9)+0.4(0.2)=0.62. Bayes’ rule gives:

P(HC∣+,D)=0.6(0.9)0.62=2731≈0.871.P(H_C\mid +,D)=\frac{0.6(0.9)}{0.62} =\frac{27}{31}\approx0.871.

A negative result has probability 0.380.38, and:

P(HC∣−,D)=0.6(0.1)0.38=319≈0.158.P(H_C\mid -,D)=\frac{0.6(0.1)}{0.38} =\frac{3}{19}\approx0.158.

After a positive result, choose the code repair. After a negative result, choose the environment repair. The overall probability of success is:

P(success after D)=P(HC,+∣D)+P(HE,−∣D)=0.54+0.32=0.86.P(\text{success after }D) =P(H_C,+\mid D)+P(H_E,-\mid D) =0.54+0.32=0.86.

The diagnostic has improved the decision before fixing anything. If it costs 0.050.05 utility units, the net expected utility is 0.810.81, compared with 0.600.60 for acting immediately. In this simplified setup, the diagnostic is worthwhile whenever its cost is less than 0.260.26.

More generally, let bb be the current distribution over hypotheses, u(a,H)u(a,H) the utility of a final action under hypothesis HH, and cDc_D the diagnostic cost. Define:

Vnow(b)=max⁡aEH∼b[u(a,H)],VD(b)=Eo∣b,D ⁣[max⁡aEH∣o,D,b[u(a,H)]]−cD.\begin{aligned} V_{\mathrm{now}}(b) &=\max_a\mathbb E_{H\sim b}[u(a,H)],\\ V_D(b) &=\mathbb E_{o\mid b,D}\!\left[ \max_a\mathbb E_{H\mid o,D,b}[u(a,H)] \right]-c_D. \end{aligned}

The diagnostic is preferable when VD(b)>Vnow(b)V_D(b)>V_{\mathrm{now}}(b). This calculation assumes that observing preserves the available final actions and has no consequence beyond the modeled cost. A disruptive test, a missed deadline, or an additional possible cause would change the comparison.

I like this formulation because it asks what information is worth for a decision. A diagnostic might reveal something interesting yet never change the preferred action. In that case, it has no decision value here before accounting for cost. We do not need to attach an arbitrary curiosity bonus to information that already improves expected task utility.

The broader idea connects to dual control: actions can influence both the system and what the controller learns about it. Klenske and Hennig examine that connection in approximate Bayesian reinforcement learning. Our diagnostic is the simple information-only case. Klenske and Hennig, 2016.

Recovery needs a definition

The debugging loop also raises a question that I would hesitate to answer with a success rate alone: what happens after the agent makes a mistake?

An incorrect edit might trigger a useful test, a rollback, and a revised hypothesis. It might instead trigger a chain of speculative edits that destroys the original failing case. Both trajectories contain feedback. Their responses to the same disturbance are very different.

Control theory gives stability a precise meaning once we specify a state, dynamics, and a notion of deviation. For a language agent, “it retries less” or “it sounds less confused” is not yet a stability result. Even useful investigation need not reduce uncertainty at every step. A surprising observation can reveal that the agent was overconfident.

I would begin with a narrower, testable definition of recovery. Give the agent a reproducible failing task, introduce one declared disturbance, and record whether it reaches a verified solution or an explicit unresolved state within a fixed allowance. A delayed result, a misleading error message, and a stale artifact test different weaknesses. They should be analyzed separately.

A comparison should include false completion claims, repeated actions that add no evidence, resource use, and whether the original task remains recoverable. Matching the model, tools, initial task, and budget would help isolate the effect of a proposed memory or feedback mechanism. This is an evaluation proposal, not a result demonstrated by this essay.

Budgets and permissions also belong in the architecture. If an action has cost ctc_t and the allowance is BB, the execution system can enforce:

∑t=0τ−1ct≤B\sum_{t=0}^{\tau-1}c_t\leq B

at the stopping time τ\tau, reserving sufficient budget before launching work. An expected-cost penalty alone does not enforce a per-run cap. Likewise, if a file must not be modified, that restriction belongs in the available action set, not only in the agent’s preference for avoiding a penalty.

Stopping within budget is not the same as solving the task. It does keep “I do not know yet” distinct from an indefinite sequence of attempts.

Creating feedback that can challenge a belief

The diagnostic example assumed a trustworthy likelihood model. Real debugging rarely supplies those numbers. The agent must decide which test could distinguish explanations, and then investigate whether the test behaves as expected.

Suppose it suspects that a dependency update caused the failure. It could compare the same code and input under the old and new dependency versions, keeping other conditions fixed and recording the exact environments. If the failure follows the version change, that is more useful evidence than another speculative edit. Repetition or further controls may still be needed to separate the effect from randomness or other differences.

This is an intervention question. Observing that failures occur in environments with a particular dependency is not generally equivalent to asking what would happen if we changed that dependency:

P(Y∣X=x)need not equalP(Y∣do⁡(X=x)).P(Y\mid X=x)\quad\text{need not equal}\quad P(Y\mid\operatorname{do}(X=x)).

Here XX is the dependency version and YY a failure outcome. The second expression describes setting XX through an intervention in a causal model. Pearl’s treatment makes explicit why causal conclusions require assumptions beyond an observed association. Pearl, 2010.

A tool call can implement an intervention, but its mere execution does not establish a cause. The agent needs a comparison, predictions that could differ, and a record of what else changed. Editing several components and seeing a passing test may help complete a task while leaving the original explanation unresolved.

This is where the control perspective leads naturally toward experimentation. When passive observations cannot distinguish the possibilities that change the next decision, the agent can choose an action specifically to obtain better evidence. That ability belongs comfortably within learning and control. Scientific work adds further obligations about the claim, the comparison, and whether the conclusion survives beyond the immediate case.

The question I would ask of an agent

A tool inventory tells me which interventions and observations are possible. A successful demonstration tells me that one trajectory worked. To understand the system, I want to know how it behaves when the world contradicts its plan.

Which observation would make it abandon its current explanation? Does its memory preserve that observation accurately? Can it choose a measurement that distinguishes the alternatives? And when the evidence remains inconclusive, can it stop without turning uncertainty into a claim of success?

Those questions connect the parts of the loop that are easy to evaluate separately: reasoning, tools, memory, and verification. Their interaction determines the behavior we actually rely on.

For me, the most interesting next step is the move from receiving feedback to designing it. A debugging agent that reruns a test can detect a failure. One that constructs a controlled comparison may learn why the failure occurs. Understanding what makes that comparison convincing is the next question I want to explore.
